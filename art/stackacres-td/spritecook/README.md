# SpriteCook props for the top-down Homestead

A second art source alongside `rich/` (generated by script) and `pixellab/` (the people).
SpriteCook draws the standing props: buildings, trees, bushes and yard clutter.

Nothing here ships yet. `build.py` writes `out/`, `preview.py` renders the Homestead with
those sprites swapped in so you can look at it. `public/stackacres-td/` is untouched.

## Run it

```
python3 art/stackacres-td/spritecook/build.py      # source/ -> out/
python3 art/stackacres-td/spritecook/preview.py    # out/ -> review/
```

## How the art is made

Generated through the SpriteCook MCP tools, model `gpt-image-2` at `quality="low"`, which is
2 credits an image. `assets.json` records the asset id behind each file in `source/`, so a
follow-up generation can reuse one as a style reference instead of starting over.

Three things that mattered:

- **The rig's own art sets the camera.** `source/view-reference.png` is nine current sprites
  stitched into one strip. It is uploaded and passed as `reference_asset_id` on every call, with
  the prompt telling the model to copy that camera exactly. This is the only thing that reliably
  held the flat top-down front view. Describing it in words did not: "orthographic, no perspective
  convergence, no side wall" squashed a farmhouse into a 14px sliver, and the first pass without a
  reference drew everything with two visible faces, which read as isometric.
- **A finished building sets the style.** The barn goes in `style_asset_ids` on everything after
  it. One trap: a *low resolution* asset used this way teaches the model chunky pixels, and the
  next output came back 34px wide.
- **Three props per sheet, not six.** One generation holds several props with space between them
  and `build.py` splits them by connected alpha. Six is cheapest, but six small objects on one
  canvas come back about 12px each, which is unusable. Three, each told to fill its share of the
  frame, is the size that survives. Pass `smart_crop=False` so the model keeps the full canvas.

SpriteCook returns about 90 to 320px art with soft shading and thousands of colours, so
`build.py` trims it, box-downscales it on premultiplied alpha, hardens the alpha edge and
quantises to 32 colours at the prop's real size from `area.json`.

## What is worth taking and what is not

Compared at game size against the rig's sprites:

- **Better:** farmhouse, barn, workshop, oak, sapling, both bushes, well, coop, signpost,
  crate, barrel, hay bale, woodpile, trough, stump.
- **Worse, so `preview.py` keeps the rig's:** the pine (the generated one is a thin spike
  where the rig's has a full silhouette) and both rocks (they come back mossy green and stop
  reading as stone).

The pattern is size. Above roughly 20px a generated prop carries far more interior detail
than hand-placed grids can. Below that the rig's sprites, authored at their real size, hold
their shape better. Legibility is the test, not richness.

## Open pieces before this could ship

- **Trees lose their wind sway.** A tree in `area.json` is a trunk frame plus a separate
  canopy frame the engine sways. `build.py` writes `<tree>-canopy.png` and `<tree>-trunk.png`
  by splitting at the shoulder of the canopy, but nothing has rendered them yet.
- **The prop atlas is built by `areas/rig/export.py`,** which cannot run in a fresh checkout
  (see `HANDOFF.md`). Landing these means either fixing that or patching the atlas and
  `area.json` in place.
- **Only the Homestead is covered.** The other seven areas reuse many of the same props but
  have their own.
- **Shadows.** The rig casts a prop's shadow into `ground-<f>.png` from the old silhouette,
  so a new sprite with a different footprint needs its shadow redrawn.
